# Repository Guidelines

## Project structure

This is the personal portfolio website for imomadjid.com, built with TanStack Start, React, TypeScript 7, Vite+, Tailwind CSS v4, and Cloudflare Workers. Keep content accurate and personal. Do not invent projects, experience, achievements, or testimonials.

- `src/routes/` contains file-based routes. `index.tsx` defines `/`; `__root.tsx` defines the document shell and stylesheet link.
- `src/router.tsx` creates the router. Start generates `src/routeTree.gen.ts` during development and builds. Keep it committed; do not edit it manually or run a separate Router CLI against it.
- `src/styles.css` imports Tailwind and holds global styles and theme extensions. Its `dark` variant follows `data-scene-tone` inside the Sunlit scene; do not override text colors with unlayered CSS.
- Allo is upstream's unmodified variable Friendly webfont from v1.0.3 (`public/fonts/allo/AlloVariableFriendly.woff2`: weight 100 to 900, optical size 9 to 32, no roundness axis). Any weight works and weight changes animate, so use `font-*` weights rather than faking bold. Its 400 matches the static Regular it replaced.
- DialKit, the Sleep Focus particles, and the `?ambientProfile` renderer timer are dev tools. Keep them behind `import.meta.env.DEV_TOOLS` so production bundles exclude them. The `dev-tools` plugin in `vite.config.ts` sets it: true in the dev server and in the dev.imomadjid.com build (`CLOUDFLARE_ENV=dev`), false in production builds. Don't gate dev tools on `import.meta.env.DEV`, which is false on the dev site. `src/env.d.ts` declares it.
- `/dev` is a playground served by the dev server and dev.imomadjid.com: route files in `src/routes/dev/` gate `head` and `component` on `import.meta.env.DEV_TOOLS` and lazy-load pages from `src/dev/`; production throws `notFound()` and the prerender filter skips `/dev`. Add test pages to `src/dev/pages.ts`.
- The Sunlit canvas is fixed to the viewport: the light comes through a window, so it stays put while the page scrolls past. Anything that casts a shadow into it scrolls with the page, so it publishes its geometry in the canvas's frame, not `main`'s, and republishes on scroll. The wand does this in `src/components/blind-wand-engine.ts` (`frameLight`, `follow`) through `wandPose` in `src/lib/sunlit-scene.ts`; the shader reads that pose as is.
- Phone tilt (`src/lib/device-tilt.ts`, with the sensor in `src/lib/tilt-sensor.ts`) turns the room against the sun: tilting a touch-first device rotates the light source about the middle of the wall, so deeper casters' shadows slide farther. The shader and the wand's CPU light (`src/components/blind-wand-light.ts`) both apply `tiltSource`; the renderer publishes the turn as `sceneLight.phoneTilt`. Rolling the phone also turns gravity within the screen, so the blind wand swings to hang plumb: the renderer publishes that angle as `sceneLight.plumb`, and the wand's swing spring pulls toward it instead of straight down the screen. Its shadow follows through `wandPose`. The renderer asks for motion access on load, which Chromium (it has `requestPermission` too) grants at once; Safari on iOS only asks from a tap, so it asks on the first tap on the page itself, not on a link or control. Tune it with the `phoneTilt` DialKit group.
- Pointer gusts (`src/lib/sunlit-gust.ts`) swing each canopy about its attachment on a spring and make leaves near the stroke flicker. Don't displace the foliage lookup by an amount that varies across the canopy: that stretches leaf shadows (an earlier gust did, by up to a quarter). Turning a whole branch keeps their shapes, and the flicker changes leaf coverage instead of position. `src/lib/sunlit-geometry.ts` holds CPU copies of the shader's sun and canopy geometry; change both together. Tune it with the `breeze` DialKit group.
- With `content.lit` on (the default; a DialKit toggle under Sunlit), the light falls on the page's content as if printed on the wall. The canvas moves above the content (`z-20`, `mix-blend-mode: hard-light`), and the material shader's `overlay` mode encodes the lit wall against the plain surface: below 0.5 multiplies by `2s` (shade), above screens with `2s - 1` (light brighter than the surface), per channel in sRGB, dithered against 8-bit banding. A fixed backdrop under the canvas (`src/components/ambient-light.tsx`) paints the plain wall the shader encodes against, so the wall looks as before. That is the interpolated surface, raised evenly through the sunrise and sunset glow (`src/lib/sunlit-backdrop.ts`, mirroring the shader's glow): hard-light brightens only by screening, which would wash dark text out to the wall's color, so the glow is encoded as shade against a brighter wall, and content outside the beam dims for a moment instead (to about 0.72 at the peak). The backdrop covers the whole canvas because `main` is `isolate`, so its group is the blend backdrop, and its box can end short of the viewport. Only the wand stays above the light (`z-30`): it hangs in front of the wall and lights itself. So nothing between the wand and `main` may form a stacking context: the homepage anchor has no z-index, and `animate-enter` fills `backwards`, not `both`, because a filled animation keeps one. `src/shaders/ambient-surface.test.ts` checks the encoding round trip and that body text keeps its contrast through the glow. To run it, and to see WebGPU in headless Chromium, a machine without a GPU needs Mesa's software Vulkan driver (`mesa-vulkan-drivers`, then `VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json`); headless screenshots still leave the WebGPU canvas out.
- The homepage's `sections` list in `src/routes/index.tsx` names its sections once: `<Section id>` renders each one's `id` and screen-reader heading, and `TableOfContents` (`src/components/table-of-contents.tsx`) lists them, fixed to the left from `lg` up, and render nothing with fewer than two sections. The whole original page (avatar row, intro, signature, and contact links) is the `about` section, which fills the first screen with `min-h-svh`. A section's `mark` replaces its visible label in the contents, which screen readers still announce; About's is the `Logo` (`src/components/logo.tsx`, the favicon's mark in `currentColor`). The logo is drawn as stroked centre-lines, so its stroke width is its weight: 12 (the favicon's outline) when active, 9.34 when inactive. The active link turns semibold, and the 2.66-unit difference is the 0.55px stem gain from 400 to 600 at 14px, so text and mark change weight together. Add or rename a section in that list. The contents are hidden below `lg` until a mobile design exists. Random bullshit (`projects`) follows About: a `ProjectList` of public repos (`src/components/project-list.tsx`), each linking to its live site or else its repo. Hovering or focusing a row flies a shared 16:9 preview just after its title, its bottom on the title's text bottom, and plays that project's media (`src/components/project-preview-media.tsx`): a looping muted video per theme (VP9 WebM with an H.264 MP4 fallback and a WebP poster) or a still. The files live in `src/assets/projects/<project>/`, named `<theme>.webm`, `<theme>.mp4`, and `<theme>.webp`, and `src/lib/project-media.ts` imports them so Vite content-hashes them into `/assets/`. Videos load only when played, plus the rows next to the playing one unless the visitor is saving data, and the media crossfades through a blur. The Gallery follows Random bullshit. The `draftSections` there (Guestbook) render only with `DEV_TOOLS`, so production never shows them; Guestbook is a stand-in that says Coming soon. Move a section into the production list once it's ready, and don't fill the stand-ins with invented content.
- The Gallery (`src/components/gallery.tsx`) shows Imo's camera (Fujifilm's X-T30 product photo cut out of its white background, `src/assets/camera/`) beside its body and lens names, the first `featuredCount` photos, and a See more tile (a 4x4 grid of thumbnails shown at 2x, which zooms out on hover, or on keyboard focus where the pointer is fine, never on a touch screen, or below `sm` a plain 2x2 grid that doesn't zoom; it uses the 640 px photos where a resting cell outgrows the 240 px thumbnails' crop) that opens every photo in a Base UI Dialog. Where WebGPU runs, the tile draws the 4x4 grid in a shader (`src/lib/gallery-warp.ts`, `src/shaders/gallery-warp.wgsl`) whose middle zooms ahead of its edges, and the CSS grid underneath is the fallback, which returns if the device is lost or a frame fails. Featured photos (`src/components/gallery-photo-tile.tsx`) zoom within their frames on hover with the same ring motion (`src/lib/ring-motion.ts`, `src/shaders/rings.wgsl`, `src/lib/gallery-photo-zoom.ts`), and a click opens the photo full screen (`src/components/gallery-lightbox.tsx`): it flies out of its tile as a quad whose corners each move on their own spring without bounce (`src/lib/gallery-flight.ts`, `src/lib/flight-springs.ts`, `src/shaders/gallery-flight.wgsl`), after Apple's app open as Raphael Salaja takes it apart: the corner farthest from its corner of the viewport leads on the quickest spring, and each other one follows on a slower one in proportion to how much shorter its way is (`cornerLags`), so corners as far as each other move together. The springs spread either side of the response, by up to `expand.spread` of it (half, as Apple spreads its rows), so a centred tile moves on the response itself. It flies back the other way round, quicker than the open, as Apple's app close does: the corner nearest its place in the tile lands first and the far side trails in. A close during the open turns the corners around with their speed rather than restarting them; only Escape can send one, since a click beside the photo waits for the open to land, so a second click where the tile was doesn't send it straight back (the See more overlay's clicks wait the same way, and its close button, which floats at the bottom middle, waits out every flight: the flight canvas draws above it). Closing, both dialogs hand focus back to what opened them (`returnFocus`), as keyboard focus only if a key opened them: Base UI would give the photo's back to the See more tile, the outer dialog's trigger, whose keyboard focus zooms its grid out. The flight starts with whatever copy of the photo is decoded (hovering a featured photo or an overlay photo warms the 1600 px file); a click starts decoding the 1600 px file, and the flight switches to it mid-flight as soon as it is ready (`sharpen`), so a tap on a phone sharpens while the photo moves, not after it lands. The flight canvas sits above the Sunlit layer, so the flying photo is unlit: on landing back in its tile it fades out over the lit tile (`expand.relight`), bringing the light and shadows back in gradually. The See more overlay (`src/components/gallery-overlay.tsx`) lays every photo out in four full-width masonry columns, or two below `sm` (`useOverlayColumns`, `src/lib/gallery-masonry.ts`), the tile's first: the tile is a grid as many cells square as the overlay has columns, and its cell in row r and column c is row `tileStartRow` + r of column c (one row down on a phone, so its 2x2 lands mid-screen; none with four columns), so opening it flies those photos out of the tile's cells (`src/lib/see-more-grid.ts` places them as the tile shows them: the 2x2 whole, the 4x4 zoomed out or at the 2x crop, whose outer cells start behind the tile's edge) into their masonry cells, all in one pass (`src/shaders/gallery-cells-flight.wgsl`), their corners led across all of them as a single photo's are. Closing, they land straight in the tile as it shows them, in one motion: the cells are clipped to the tile's rounded edge grown by a margin, the farthest any corner still is from its place in the tile, with an edge softened outward by half of it, so the outer cells of the 2x crop slide under the rim, fading, as they land, and out from under it opening. The middle four can't be clipped (their places are inside the tile), and at margin 0 the edge is the tile's own. Scrolled down, the photos in view fly home instead: each masonry column's first cells on screen, as many as it leads with, fly into the tile's column it leads and crossfade into its photos on the way (`closingCells`), so the close starts from what's on screen however long the list grows. The tile stays empty while its photos are out. Photos in the overlay open the same lightbox, nested in that dialog (its root holds the lightbox, and its backdrop needs `forceRender`), so closing the photo flies it back into its cell with the overlay still open. Overlay photos zoom on hover as the featured photos do (`OverlayPhoto`), each starting its renderer on its first hover or focus, so the overlay doesn't open two dozen canvases. The lightbox marks whatever it lifted the photo out of with `data-lifted`, which those buttons hide with `data-lifted:invisible`. Both fly on one canvas, `useFlightStage` (`src/components/gallery-flight-stage.tsx`). Behind an open photo or the overlay, everything below About shrinks to `recede.scale` about the middle of the viewport, as iOS shrinks the Home Screen behind an opening app (`src/lib/page-recede.ts`): a `[data-recede]` wrapper in `src/routes/index.tsx` scales in CSS on a spring sampled into a `linear()` easing (`cssSpring`), only while receded, so it forms a stacking context only then; About stays out because it holds the wand, and the Sunlit layers stay still. A photo opened from the overlay shrinks the overlay's masonry behind it the same way (it is a `[data-recede]` wrapper too, so the point it shrinks about counts the popup's scroll). Each grows back as its close starts, so a flight lands where its tile or cell will be at full size (`fullScaleRect`). The dialogs' backdrops are thin enough (60%) for the shrink to show. Without WebGPU, the tiles zoom in CSS and the photo and the overlay fade in. Every Gallery renderer shares one device (`src/lib/gallery-gpu.ts`) and starts as the Gallery nears the viewport (`src/components/use-gallery-renderer.ts`). `src/lib/gallery-settings.ts` holds the timing (the `Gallery` DialKit group); the See more warp is also tuned in `/dev/gallery-warp`. The dialogs portal to the top of the body at `z-50`, outside `main`'s stacking context, so they cover the Sunlit light and the wand; the flight canvas sits above them at `z-60`. `src/lib/gallery.ts` lists the photos in display order with alt text; reorder it to pick favourites. `tools/gallery/import.sh <Drive filenames>` pulls originals from the Drive folder through rclone, writes `src/assets/gallery/<stem>-240.webp`, `-640.webp` and `-1600.webp` stripped of EXIF (GPS included), and records sizes in `photos.json`, then `tools/gallery/metadata.ts` adds each original's exposure (shutter, aperture, ISO, focal length, exposure compensation, lens) and Fujifilm settings from its EXIF (needs exiftool). `src/lib/fuji-settings.ts` lists the recipes Imo shoots (Summer Chrome, Kodak Portra 400 v2, Reggie's Portra, Terracotta Sun) and `matchRecipe` names each photo's, or null; a recipe states only its published settings, and matching ignores exposure. Each `GalleryPhoto` carries `exposure`, `settings` and `recipe` for the expanded photo. Under an open photo, `ExposureReadout` (`src/components/gallery-exposure.tsx`) shows its exposure as a camera's display does, from the photo's left edge, each label (muted in light mode, yellow in dark) beside its readout in tabular slashed-zero figures, formatted in `src/lib/exposure-format.ts` (`ƒ6,3`, a decimal comma, `0,8″`, `−⅓`, `±0`), and the recipe `matchRecipe` names, if any, as an underlined link to its source on the right. It shows exposure only, not the lens or the Fujifilm settings. Where the photo is too narrow for one line, the row grows wider than it, centred under it, up to the viewport's margins, and wraps only past that (`readoutRow` and `wrapLines` in `src/lib/readout-layout.ts`), as on a phone, so its lines depend only on the viewport. The lightbox renders it first (`flushSync`) and measures its items (`measureReadout`), and `fullScreenLayout` leaves as many lines under the photo as they take (`readoutSpace`), the flight's landing included. The readouts come up while the photo settles, a transition delay of `readout.start` of the open's response from takeoff, so the two overlap: each rises out of a blur on `readout.motion`'s spring, `readout.stagger` after the one before (the `Gallery` DialKit group), and they go together as the close starts. The recipe link takes clicks only while it shows, and the lightbox focuses its popup on open, not the link. Add a recipe there when a new one is in use; to backfill metadata alone, run `metadata.ts` on the originals. The homepage lazy-loads the section, so its code and photos stay out of the first load.
- Static glass (Button's `glass="static"`, the homepage `LinkButton`) shares the surface classes in `src/lib/glass.ts`; the layer stack is the `glass-surface` utility in `src/theme.css`, drawing from `--glass-fill` and `--glass-shadow` in `src/styles.css`. The light values are fitted to two iOS 26 captures at 3x, on white and on `#f2f1f6` (`/dev/glass` holds both reference frames); a single white backdrop cannot separate fill color from opacity, so refit against both. The dark values are fitted the same way on `#1c1c1e` and black. Dark glass is near-additive light, so keep it a white alpha fill: `mix-blend-mode: plus-lighter` breaks under the buttons' `isolate`.
- Interface sound is cuelume in its `press` theme, used as cuelume intends. `startSounds` in `src/lib/sound.ts` (run from `__root.tsx`) sets the theme and calls `bind()`. Mark a control with its cue's `data-cuelume-*` attribute, so it plays as the press goes down and lets go as it lifts: the Gallery's photo tiles carry `data-cuelume-open`, its overlay's close button `data-cuelume-close`, the theme toggle `data-cuelume-toggle`. Call `play()` from `cuelume` only for what code decides: an Escape or backdrop close, the blind wand's gear ticks, and See more's open, a run of three opens 90 ms apart (`playOpenRun`) that cuelume's press theme walks up its own steps, A, C♯ and F♯. Pick each cue by its job from cuelume's "Which cue?" table, and play none on hover. The footer's Sound switch (`src/components/site-footer.tsx`) stores an off choice in localStorage (`imomadjid:sound`, followed across tabs; a head script marks `data-sound="off"` so the switch's word is right before hydration) and calls `unlock()` in the click that turns sound on. A gesture whose cue plays later, as the wand's ticks do from animation frames, calls `wakeSound()` in the gesture; reduced motion doesn't mute sound. cuelume 0.2.9 is vendored as `vendor/cuelume-0.2.9.tgz`, built with `npm pack` from its `v0.2.9` tag, because npm has only 0.2.8, which holds the audio device open and doesn't recover after a Safari lock; switch to the npm release once 0.2.9 is published.
- Live glass (`glass="live"` on Button and IconButton, used by the Gallery overlay's close button) refracts, frosts and tones what is behind it on WebGPU, so it works in Safari (`src/lib/live-glass.ts`, `src/shaders/live-glass*.wgsl`). WebGPU can't read the page's pixels: a `LiveGlassSourceProvider` (`src/components/live-glass.tsx`) lists the `<img>` photos and flat colour behind the glass, and without a source, without WebGPU, under reduced transparency, or on failure it draws static glass. Each draw composes that backdrop around the glass in the frost's power space, frosts it at two scales (about 30% at half of 3x, 70% about 15 pt wide, as iOS 27's regular glass does; the backdrop is composed at 3x on any screen, so the frost spreads as far in pt everywhere), bends it by a fitted bevel that folds content in from the middle at the rim, and tones it from tables over distance from the edge and normal angle that also carry the rim light, hairline and shadow. It shares the Gallery's GPU device. A source whose photos move by the browser's own scrolling sets `scrolls` and wakes the glass only on scroll: that scrolling runs off the main thread, a frame ahead of the rects the glass reads, so while the photos keep moving the glass draws them a step ahead (without it, it trails a frame, 6.7 pt at 400 pt/s). Tinted live glass isn't modelled: a `tint-*` class on the Button keeps it static.
- `tools/glass-live/` is live glass's fixture (its `README.md` walks through the loop): `scenes.ts` writes `Scenes/scenes.json` (the overlay's masonry, a line grid, ramps, sawtooths, a step and flat tones), which the SwiftUI app and `/dev/live-glass` both lay out; `capture.sh` takes iOS 27 simulator captures; `fit.py` fits the material into `src/lib/live-glass-material.json` (generated and left unformatted; refit rather than edit it); `shoot.ts` captures `/dev/live-glass?scene=` at 3x in headless Chrome (playwright-core) and `diff.py` compares the two. Ramps measure where the bevel samples from, the step's line spread measures the frost, and the grid shows the fold. The `motion-*` scenes scroll three copies of the masonry under the glass at 400 pt/s: `record.sh` records the simulator (H.264, so compare against the floor `motion.py` reports), `motion.py offsets` places each frame on the strip, `motion.ts` renders the web at those offsets, and `motion.py diff`/`video` compare them. `capture.sh motion-light@<pt>` takes lossless stills along the strip, which `fit.py` fits with the rest. `lag.ts` screencasts the web while it really scrolls (`raf`, `wheel`, `touch`) and `motion.py lag` measures how far the glass trails the page. iOS glass has no temporal behaviour: a recorded frame matches a still at its offset. The bevel's pull runs from about 23 pt at the rim (so the rim shows content from near the middle, and a gap behind it sweeps out into a cap) to 0 by 14 pt in: iOS doesn't bend the middle at all, and any pull there magnifies and smears it. It is a monotone cubic (PCHIP) through its knots in `fit.py` and the shader alike, since a linear one creases the rim; `fit.py --bevel` refits the knots to the image error of both schemes. The frost works in a power space per scheme (`gamma`, about 1.56 light, 0.70 dark: the compose pass raises the backdrop, the glass pass undoes it after mixing), and its sharp share is the backdrop at half the 3x screen's resolution on even device pixels, read back bilinearly, as iOS's line spread shows; neither linear light nor a narrow Gaussian fits as well. `fit.py` holds the motion stills at 150, 450, 750, 1050 and 1350 pt out of its searches and reports them apart.
- `wrangler.jsonc` configures the Worker. Build output goes to `dist/`. Start prerenders `/` into a static asset; the Worker handles other URLs, including the 404. `public/_headers` sets asset caching. The Worker's entry is `src/server.ts`, Start's handler plus byte ranges for `/assets/*.webm` and `/assets/*.mp4`, which `run_worker_first` routes to it: static assets answer a `Range` with the whole file, and Safari won't play video served that way.
- Its `dev` environment is a second Worker, `imomadjid-com-dev`, on dev.imomadjid.com. `bun run build:dev` builds it (`CLOUDFLARE_ENV=dev`), with the dev tools on and the site kept out of search: every page has `<meta name="robots" content="noindex">`, and the `dev-tools` plugin appends `X-Robots-Tag: noindex` to the built `_headers` and drops the sitemap from `robots.txt`. Keep `robots.txt` allowing crawlers there, or they never see the noindex. The built `dist/server/wrangler.json` records the environment, so deploy it with `--config`, as `bun run deploy:dev` does.
- `tint-*` (`src/theme.css`) colors Buttons like SwiftUI's `.tint()`: `tint-red-500`, `tint-blue-100`, arbitrary values. No opacity modifier (a translucent tint reads as disabled); use a lighter palette step instead. It sets `--btn-tint*` variables, so it cascades to nested Buttons; primary fills with it, glass lays it between `--glass-fill` and a soft-light edge shine, and the label turns white below oklch L 0.75. Don't use `bg-*` for Button color: the fill is an inner span. `cn` doesn't merge two `tint-*` classes (registering a group needs `cn/config`, +45 KB JS), so pass one.
- `tools/glass-tints/` is a SwiftUI fixture (iOS and macOS 26+) rendering Liquid Glass tinted with Tailwind colors converted to Display P3. Generate with `xcodegen generate` there. `capture.sh` takes lossless 3x PNGs from an iOS 27 simulator named `GlassTints` (iPhone 16 Pro) into `<dir>/ref`; `shoot.sh` renders `/dev/glass` at 3x into `<dir>/web`; `tintdiff.py` diffs the tinted reference frames per region. Fit against simulator captures, not macOS: macOS glass can differ, and inactive macOS windows desaturate it. Simulator glass is close to, but not the same as, the iOS 26 device captures behind untinted glass, so tinted fits are relative to plain glass.
- Shaders are `.wgsl` modules loaded by vgpu's `wgslVitePlugin`; `bunfig.toml` preloads `tools/bun-wgsl-loader.js` so Bun tests can import them. vgpu render targets need whole-pixel sizes.
- iOS Safari 26+ clips `position: fixed` and `position: sticky` layers to the viewport between its status bar and toolbar (a sticky layer overscanned past each end is cut at the bars too; checked in the simulator with a marker at its top), and `viewport-fit=cover` doesn't change that: only the page's flow draws under the bars. It also collapses its toolbar only when the document scrolls, never a scrolling layer over it. The Sunlit layers stick on touch screens, overscanned 5rem past each end; `src/lib/light-frame.ts` maps the scene back onto the viewport-sized frame. Safari also fills the area under a bar with an opaque, unblurred band where the middle of that edge hits a fixed or sticky layer about the viewport's size or a dimming layer (a translucent background with no children); with a backdrop-filter the band takes the page's colour (WebKit's `fixedContainerEdges`). So on touch screens the See more overlay lies in the page's flow and the page scrolls it (`useOverlayScrollsPage`, `holdPage` in `src/lib/dialog-layer.ts` pins `main` at its scroll until the overlay has gone), which lets the photos run under both bars and the toolbar collapse; it portals into its own `contents` layer after the dialog layer, and its dialog is `modal="trap-focus"` there, since a scroll lock would stop it. The backdrops stick, too tall to count: they portal into a `contents` layer at the top of the body (a flow root), and each cancels its own height with a top margin only, since adjacent bottom and top margins would collapse. The backdrop's colour and blur sit in a child (`GalleryBackdropFill`), so it isn't a dimming layer. The open photo's popup stays fixed and viewport-sized on purpose: its band covers the toolbar, where the clipped backdrop would leave the page showing unblurred. Keep the flight canvas `invisible` between flights: it covers the viewport, and Safari hit-tests through `pointer-events: none`. The iOS Simulator has no WebGPU adapter, so check layer extents there and the shader in the browser pane at a mobile size; Simulator Safari reaches the Mac's `localhost` directly (`xcrun simctl openurl <device> http://localhost:3000/`).

## Development and validation commands

Use Bun and update `bun.lock` with dependency changes. Node 26 is pinned in `.node-version` (fnm, CI) and `engines`; keep `@types/node` on the same major. See `README.md` and `package.json` for commands. Run `bun run deploy` only with deployment authorization.

## Coding style and naming

Let Oxfmt enforce formatting. Use PascalCase for React components and camelCase for functions and variables. Follow TanStack file-based route naming. Use type-only imports where appropriate.

Use Tailwind utilities for styling. Keep Oxfmt, Oxlint, and anti-slop settings in `vite.config.ts`. Do not add Biome. Treat `tools/oxlint/anti-slop/` as vendored code.

## Icons

- **Utility icons** (arrows, chevrons, close, external link, copy, menu): use Tabler via `@tabler/icons-react`. The Gallery overlay's close button is the first one.
- **Decorative or unconventional icons** (theme toggle, feature accents, anything the page features rather than just labels): draw Fill Duo icons with the `duotone-icons` skill in `.agents/skills/duotone-icons` (source: `imomadjid/duotone-icons`). Load the skill before drawing, and run its `lint.mjs` and `preview.mjs` scripts on the result. Put the icons next to their component, following `src/components/theme-icons.tsx`.
- Don't mix the two styles in one control. Size Tabler icons to match the Fill Duo 18px grid wherever they sit side by side.
- Restore or update local skills with `bunx skills experimental_install` and `bunx skills update`; `skills-lock.json` pins the source commit.

## Testing guidelines

Tests use `bun test` (`bun run test`). CI runs only `src/components` and `src/lib` tests and `tools/fluid-registry-files.test.ts` because the shader test needs a native WebGPU adapter. No coverage threshold is configured. For implementation changes, run `bun run check`, `bun run test`, and `bun run build` before review. Verify UI changes in a browser. For documentation-only changes, check formatting and verify affected instructions against the repository. A read-only audit does not require a build unless needed to investigate a finding. Use descriptive `*.test.ts` or `*.test.tsx` names for future tests.

Run `bun run doctor` when the task requests a full React audit or a React-related finding needs broader investigation. The full audit blocks errors; staged React Doctor warnings block commits. Review advisory findings before changing code. See `README.md` for hook and advisory tool details.

## Commits and pull requests

Use concise imperative messages with `feat:`, `fix:`, or `chore:` prefixes. Keep changes focused.

Commit on `master` in the main checkout, then push to `dev` first: `git push origin master:dev`. Pushing `dev` runs `.github/workflows/deploy.yml` and deploys dev.imomadjid.com for review. If `origin/dev` has commits `master` lacks, rebase `master` onto it before pushing. Pushing `master` itself runs the same workflow and deploys production, so push it only with deployment authorization, after the work has been checked on dev.

PRs should describe the change, link relevant issues, and report validation results. Include screenshots for visible UI changes. Never commit credentials, environment files, or generated build output.

## Fluid Functionalism surfaces

FF is a copy-in registry configured in `components.json`. Add components only when needed: `bunx shadcn@latest add @fluid/base/button --yes`. Prefer the Base UI variants (`@fluid/base/<name>`). Review source and dependencies before installation; do not overwrite local adaptations blindly.

- Keep the local `src/lib/utils.ts`, `surface-classes.ts`, and `surface-context.tsx`; restore them after `--overwrite`.
- The shadcn CLI mangles `src/styles.css` (self-referencing vars, keyframes inside `@theme`) and may rewrite `src/lib/utils.ts` or re-add `clsx`/`tailwind-merge`. Review the diff, merge tokens by hand, and keep `cn` re-exported from the `cn` package.
- FF's `src/lib/icon-context.tsx` and the `/dev` fixtures use `lucide-react`. Keep it to those files; production UI follows the icon rules above.
- `cn` resolves conflicts with tailwind-merge's default groups, so it reads the custom `text-display`/`text-title`/`text-body`/... sizes as text colors and drops one of them next to a color. Pass those through plain strings, or use the `text-[length:...]` forms in `src/lib/type-scale.ts`.
- FF components read neutral shadcn roles (`foreground`, `muted-foreground`, `border`, ...) defined in `src/styles.css`.
- The site uses FF's `pill` shape, set once by `<ShapeProvider defaultShape="pill">` in `__root.tsx`. FF components read it from context; no CSS reads the `--shape-input-radius` property the provider writes, and the base `:focus-visible` outline follows each element's own corners. The `/dev/components` shape switcher previews other shapes at runtime only.
- Add new FF registry files to `fluidRegistryFiles` in `tools/fluid-registry-files.ts` (`vite.config.ts` relaxes anti-slop rules there only), to `ignore.files` in `doctor.config.json`, to `ignoreFindings` in `.fallowrc.json`, and to the matching `@source` lists in `src/styles.css` (excluded) and `src/dev/dev.css` (scanned). `tools/fluid-registry-files.test.ts` fails if those lists drift. When a production page starts rendering an FF component, also move the runtime CSS it needs (spinner keyframes, `.scroll-fade`, `.scroll-divider`) from `src/dev/dev.css` into `src/styles.css`. `dev.css` links only under `/dev`, so site pages in dev show production CSS. Production CSS skips the playground and FF components; remove a file from the `@source not` list once a production page renders it.
- `src/theme.css` holds the shared dark variant and `@theme` mappings. `src/dev/dev.css` references it; it must not reference `src/styles.css`, or that sheet's `@source not` rules apply to the dev scan. `src/dev/dev.css` puts its utilities in the same `utilities` layer and scans every source, not only the playground, so it is a complete, ordered utility set that wins over `src/styles.css` on `/dev`; narrowing that scan lets its plain utilities override variants only `styles.css` emits.

The root provides level 1 and paints `bg-surface-1`. Surface colors and shadows live in `src/styles.css`; light mode uses shadows above white surfaces, while dark mode also increases background brightness. Activate dark tokens with `.dark` on `<html>`.

- Read the parent level with `useSurface()` from `#/lib/surface-context`. For custom overlays, use `normalizeSurfaceLevel(parent + offset)` from `#/lib/surface-classes`: menus/popovers use `+2`, dialogs use `+4`, capped at 8.
- Paint the container with `surfaceClasses(level)` and wrap its children in `<SurfaceProvider value={level}>`. Context alone does not paint a background. Preserve this context through portals.
- Keep FF components' existing elevation logic. Do not add a second offset around them.
- Use `surfaceClasses(level, shadowLevel)` when a component deliberately keeps its shadow depth separate. Avoid arbitrary background colors or shadows for elevated panels.
- Never interpolate `bg-surface-${level}` or `shadow-surface-${level}`. Use the literal lookup helpers so Tailwind emits the classes. Use `bg-hover` and `bg-active` for interaction overlays.
- Check nested surfaces in light and dark modes, including focus and clipping. See [upstream surface rules](https://www.fluidfunctionalism.com/docs/surfaces).
