## Skill Loading

Before editing files for a substantial task:

- Run `bun run intent list` from the workspace root to see available local skills.
- If a listed skill matches the task, run `bun run intent load '<package>#<skill>'` before changing files.
- Use the loaded `SKILL.md` guidance while making the change.
- Multiple matches: prefer the most specific local skill for the package or concern you are changing; load additional skills only when the task spans multiple packages or concerns.

# Repository Guidelines

## Project structure

This is the personal portfolio website for imomadjid.com, built with TanStack Start, React, TypeScript 7, Vite+, Tailwind CSS v4, and Cloudflare Workers. Keep content accurate and personal. Do not invent projects, experience, achievements, or testimonials.

- `src/routes/` contains file-based routes. `index.tsx` defines `/`; `__root.tsx` defines the document shell and stylesheet link.
- `src/router.tsx` creates the router. Start generates `src/routeTree.gen.ts` during development and builds. Keep it committed; do not edit it manually or run a separate Router CLI against it.
- `src/styles.css` imports Tailwind and holds global styles and theme extensions. Its `dark` variant follows `data-scene-tone` inside the Sunlit scene; do not override text colors with unlayered CSS.
- Allo is upstream's unmodified variable Friendly webfont from v1.0.3 (`public/fonts/allo/AlloVariableFriendly.woff2`: weight 100 to 900, optical size 9 to 32, no roundness axis). Any weight works and weight changes animate, so use `font-*` weights rather than faking bold. Its 400 matches the static Regular it replaced.
- The Sleep Focus particles (`?sleep` on the homepage) and the `?ambientProfile` renderer timer are dev tools. Keep them behind `import.meta.env.DEV_TOOLS` so production bundles exclude them. The `dev-tools` plugin in `vite.config.ts` sets it: true in the dev server and in the dev.imomadjid.com build (`CLOUDFLARE_ENV=dev`), false in production builds. Don't gate dev tools on `import.meta.env.DEV`, which is false on the dev site. `src/env.d.ts` declares it.
- `/dev` is a playground served by the dev server and dev.imomadjid.com: route files in `src/routes/dev/` gate `head` and `component` on `import.meta.env.DEV_TOOLS` and lazy-load pages from `src/dev/`; production throws `notFound()` and the prerender filter skips `/dev`. Add test pages to `src/dev/pages.ts`.
- The social card `public/og.jpg` is `/dev/og` (`src/dev/og-fixture.tsx`): the Sunlit wall lit from the right, its slats and leaves tapering off into plain wall to the left, with a faded logo in the middle. `bun tools/og/shoot.ts` captures it from the running dev server in Chrome at 1200 x 630, aiming the beam with the pointer; the leaves move, so rerun it for another frame. Query overrides (`?logo=72&foliage.scale=0.7`, read by `src/dev/scene-tuning.ts`) tune it without editing the fixture.
- `/dev/story` (`src/dev/story-fixture.tsx`) is the Sunlit wall alone for a portrait story video, its leaves and slats scaled down for a tall screen. `bun tools/story/record.ts <out.mp4>` records it at 1080 x 1920 and 60 fps through ffmpeg, from day into a sunset to night (it switches the page to dark), taking over the page's `requestAnimationFrame` to step its clock one frame per screenshot, so the video plays at full rate however slow the capture is (about 0.3 s a frame). The same query overrides apply, plus `?sunset=` for the sunset's length.
- The Sunlit canvas is fixed to the viewport: the light comes through a window, so it stays put while the page scrolls past. Anything that casts a shadow into it scrolls with the page, so it publishes its geometry in the canvas's frame, not `main`'s, and republishes on scroll. The wand does this in `src/components/blind-wand-engine.ts` (`frameLight`, `follow`) through `wandPose` in `src/lib/sunlit-scene.ts`; the shader reads that pose as is.
- Phone tilt (`src/lib/device-tilt.ts`, with the sensor in `src/lib/tilt-sensor.ts`) turns the room against the sun: tilting a touch-first device rotates the light source about the middle of the wall, so deeper casters' shadows slide farther. The shader and the wand's CPU light (`src/components/blind-wand-light.ts`) both apply `tiltSource`; the renderer publishes the turn as `sceneLight.phoneTilt`. Rolling the phone also turns gravity within the screen, so the blind wand swings to hang plumb: the renderer publishes that angle as `sceneLight.plumb`, and the wand's swing spring pulls toward it instead of straight down the screen. Its shadow follows through `wandPose`. The renderer asks for motion access on load, which Chromium (it has `requestPermission` too) grants at once; Safari on iOS only asks from a tap, so it asks on the first tap on the page itself, not on a link or control. Its settings are `phoneTilt` in `src/lib/ambient-settings.ts`.
- Pointer gusts (`src/lib/sunlit-gust.ts`) swing each canopy about its attachment on a spring and make leaves near the stroke flicker. Don't displace the foliage lookup by an amount that varies across the canopy: that stretches leaf shadows (an earlier gust did, by up to a quarter). Turning a whole branch keeps their shapes, and the flicker changes leaf coverage instead of position. `src/lib/sunlit-geometry.ts` holds CPU copies of the shader's sun and canopy geometry; change both together. Its settings are `breeze` in `src/lib/ambient-settings.ts`.
- With `content.lit` on (the default, in `src/lib/ambient-settings.ts`), the light falls on the page's content as if printed on the wall. The canvas moves above the content (`z-20`, `mix-blend-mode: hard-light`), and the material shader's `overlay` mode encodes the lit wall against the plain surface: below 0.5 multiplies by `2s` (shade), above screens with `2s - 1` (light brighter than the surface), per channel in sRGB, dithered against 8-bit banding. A fixed backdrop under the canvas (`src/components/ambient-light.tsx`) paints the plain wall the shader encodes against, so the wall looks as before. That is the interpolated surface, raised evenly through the sunrise and sunset glow (`src/lib/sunlit-backdrop.ts`, mirroring the shader's glow): hard-light brightens only by screening, which would wash dark text out to the wall's color, so the glow is encoded as shade against a brighter wall, and content outside the beam dims for a moment instead (to about 0.72 at the peak). The backdrop covers the whole canvas because `main` is `isolate`, so its group is the blend backdrop, and its box can end short of the viewport. Only the wand stays above the light (`z-30`): it hangs in front of the wall and lights itself. So nothing between the wand and `main` may form a stacking context: the homepage anchor has no z-index, and `animate-enter` fills `backwards`, not `both`, because a filled animation keeps one. `src/shaders/ambient-surface.test.ts` checks the encoding round trip and that body text keeps its contrast through the glow. To run it, and to see WebGPU in headless Chromium, a machine without a GPU needs Mesa's software Vulkan driver (`mesa-vulkan-drivers`, then `VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json`); headless screenshots still leave the WebGPU canvas out.

The logo is drawn as stroked centre-lines, so its stroke width is its weight: 12 (the favicon's outline) when active, 9.34 when inactive. The active link turns semibold, and the 2.66-unit difference is the 0.55px stem gain from 400 to 600 at 14px, so text and mark change weight together. Add or rename a section in that list. The contents are hidden below `lg` until a mobile design exists. Where WebGPU runs, the tile draws the 4x4 grid in a shader (`src/lib/gallery-warp.ts`, `src/shaders/gallery-warp.wgsl`) whose middle zooms ahead of its edges, and the CSS grid underneath is the fallback, which returns if the device is lost or a frame fails. Featured photos (`src/components/gallery-photo-tile.tsx`) zoom within their frames on hover with the same ring motion (`src/lib/ring-motion.ts`, `src/shaders/rings.wgsl`, `src/lib/gallery-photo-zoom.ts`), and a click opens the photo full screen (`src/components/gallery-lightbox.tsx`): it flies out of its tile as a quad whose corners each move on their own spring without bounce (`src/lib/gallery-flight.ts`, `src/lib/flight-springs.ts`, `src/shaders/gallery-flight.wgsl`), after Apple's app open as Raphael Salaja takes it apart: the corner farthest from its corner of the viewport leads on the quickest spring, and each other one follows on a slower one in proportion to how much shorter its way is (`cornerLags`), so corners as far as each other move together. The springs spread either side of the response, by up to `expand.spread` of it (half, as Apple spreads its rows), so a centred tile moves on the response itself. It flies back the other way round, quicker than the open, as Apple's app close does: the corner nearest its place in the tile lands first and the far side trails in. A close during the open turns the corners around with their speed rather than restarting them; only Escape can send one, since a click beside the photo waits for the open to land, so a second click where the tile was doesn't send it straight back (the See more overlay's clicks wait the same way, and its close button, which floats at the bottom middle, waits out every flight: the flight canvas draws above it). Closing, both dialogs hand focus back to what opened them (`returnFocus`), as keyboard focus only if a key opened them: Base UI would give the photo's back to the See more tile, the outer dialog's trigger, whose keyboard focus zooms its grid out. The flight starts with whatever copy of the photo is decoded (hovering a featured photo or an overlay photo warms the 1600 px file); a click starts decoding the 1600 px file, and the flight switches to it mid-flight as soon as it is ready (`sharpen`), so a tap on a phone sharpens while the photo moves, not after it lands. The flight canvas sits above the Sunlit layer, so the flying photo is unlit: on landing back in its tile it fades out over the lit tile (`expand.relight`), bringing the light and shadows back in gradually. The See more overlay (`src/components/gallery-overlay.tsx`) lays every photo out in four full-width masonry columns, or two below `sm` (`useOverlayColumns`, `src/lib/gallery-masonry.ts`), the tile's first: the tile is a grid as many cells square as the overlay has columns, and its cell in row r and column c is row `startRow` + r of column c (`tileCells`: one row down on a phone, so its 2x2 lands mid-screen; none with four columns), so opening it flies those photos out of the tile's cells (`src/lib/see-more-grid.ts` places them as the tile shows them: the 2x2 whole, the 4x4 zoomed out or at the 2x crop, whose outer cells start behind the tile's edge) into their masonry cells, all in one pass (`src/shaders/gallery-cells-flight.wgsl`), their corners led across all of them as a single photo's are. Closing, they land straight in the tile as it shows them, in one motion: the cells are clipped to the tile's rounded edge grown by a margin, the farthest any corner still is from its place in the tile, with an edge softened outward by half of it, so the outer cells of the 2x crop slide under the rim, fading, as they land, and out from under it opening. The middle four can't be clipped (their places are inside the tile), and at margin 0 the edge is the tile's own. Scrolled down, the photos in view fly home instead: each masonry column's first cells on screen, as many as it leads with, fly into the tile's column it leads and crossfade into its photos on the way (`closingCells`), so the close starts from what's on screen however long the list grows. The tile stays empty while its photos are out. Photos in the overlay open the same lightbox, nested in that dialog (its root holds the lightbox, and its backdrop needs `forceRender`), so closing the photo flies it back into its cell with the overlay still open. Overlay photos zoom on hover as the featured photos do (`OverlayPhoto`), each starting its renderer on its first hover or focus, so the overlay doesn't open two dozen canvases. The lightbox marks whatever it lifted the photo out of with `data-lifted`, which those buttons hide at once (`data-lifted:invisible`), for a takeoff or a landing; while a step hands the photo's place from one tile to another, `data-step-fade` (`fadeHandOff`) gives both a transition, so the old one fades back in and the new one out. Both fly on one canvas, `useFlightStage` (`src/components/gallery-flight-stage.tsx`). Behind an open photo or the overlay, everything below About shrinks to `recede.scale` about the middle of the viewport, as iOS shrinks the Home Screen behind an opening app (`src/lib/page-recede.ts`): a `[data-recede]` wrapper in `src/routes/index.tsx` scales in CSS on a spring sampled into a `linear()` easing (`cssSpring`), only while receded, so it forms a stacking context only then; About stays out because it holds the wand, and the Sunlit layers stay still. A photo opened from the overlay shrinks the overlay's masonry behind it the same way (it is a `[data-recede]` wrapper too, so the point it shrinks about counts the popup's scroll). Each grows back as its close starts, so a flight lands where its tile or cell will be at full size (`fullScaleRect`). The dialogs' backdrops tint the page 80%, still thin enough for the shrink to show. Their fill (`GalleryBackdropFill`) blurs and tints in from nothing as they open and back out as they close, keyed off Base UI's `data-starting-style` and `data-ending-style` on the backdrop (Base UI times the exit by the popup, not the backdrop): the backdrop itself never fades, since an ancestor below full opacity is a backdrop root, which the blur can't see past, so the page would stay sharp under the fading tint and blur all at once at the end. Without WebGPU, the tiles zoom in CSS and the photo and the overlay fade in. It shows exposure only, not the lens or the Fujifilm settings. Its bar is the same under every photo of the set the photo opened from (`readoutBar` in `src/lib/readout-layout.ts`): from `sm` up, one row under the photo, the recipe flush right (its name's right edge on its label's, the arrow hanging outside), as wide as the set's widest photo shows (a landscape one's), so a portrait photo narrows the photo but not the bar, centred on the viewport, and wider only where its cells need it; below `sm` (`readoutGrid`, which also sets the photo's margin), a grid of three columns over two rows pinned to the bottom margin, so a step between shapes doesn't move it. `fullScreenLayout` leaves the room it takes under the photo (`readoutSpace`), the flight's landing included. Each value stacks every value its cell takes across the set unseen in the same grid area (`RollingValue`), so each cell, and a phone's columns, are as wide as their widest value and nothing moves as values change or a recipe comes and goes: Scritto's own width animation starts a frame late, which would jump the cells after a value that grows. The recipe's cell is there whenever the set has a recipe. Scritto sits in an `aria-hidden` span, and each value is read from an `sr-only` copy. The readouts come up while the photo settles, a transition delay of `readout.start` of the open's response from takeoff, so the two overlap: each rises out of a blur on `readout.motion`'s spring, `readout.stagger` after the one before, and they go together as the close starts. The recipe link takes clicks only while it shows, and the lightbox focuses its popup on open, not the link. Once a photo has landed, static glass arrows either side at the floating `4xl` size (`LightboxArrows`, hidden on touch screens, which swipe), the arrow keys (without modifiers, as Alt+Left is Back, or a held key's repeats) and a horizontal swipe step through its set, and a swipe down closes it (the popup's `touch-action` allows pinching only, since a pan would cancel the swipe): the featured photos from the page, every photo in the overlay's order from the overlay (`openPhoto`'s last argument). Each tile carries `data-photo-id` inside a `data-gallery-set`, where the lightbox finds the new photo's tile; it hands the photo's place (`data-lifted`, the close's landing, the returned focus) to that tile, and scrolls it smoothly into view behind the backdrop if its full-size box isn't, as little as it takes (`revealReceded` in `src/lib/page-recede.ts`); a close finishes that scroll at once before it measures where to land. The point a receded page shrinks about is kept in its own box, so it scrolls with the page and `fullScaleRect` still holds; re-centring it after a scroll would shift the shrunken page by its scale's share of the scroll in one frame. Each full-screen photo sits in a frame of its own at its own rect (`PhotoLayers`), clipped by a rounded `clip-path: inset()` to the newest photo's rect (`layerMotion`): a leaving landscape is cut in to an incoming portrait, and an incoming photo grows out of the outline of the photo before it (@starting-style), so the outline moves between the shapes on `navigate.frame`'s spring while nothing resizes. A frame that resized (tried) either zoomed the photos or let the last of its way snap. The leaving photo stays opaque under the new one, which fades up over it, so the middle never dims; where the outline widens the new one fades quicker (`navigate.reveal`), so its sides arrive nearly opaque. Above `sm`, the readout's top follows a photo of another shape's bottom on the outline's spring. - Live glass (`glass="live"` on Button and IconButton, used by the Gallery overlay's close button) refracts, frosts and tones what is behind it on WebGPU, so it works in Safari (`src/lib/live-glass.ts`, `src/shaders/live-glass*.wgsl`). WebGPU can't read the page's pixels: a `LiveGlassSourceProvider` (`src/components/live-glass.tsx`) lists the `<img>` photos and flat colour behind the glass, and without a source, without WebGPU, under reduced transparency, or on failure it draws static glass. Each draw composes that backdrop around the glass in the frost's power space, frosts it at two scales (about 30% at half of 3x, 70% about 15 pt wide, as iOS 27's regular glass does; the backdrop is composed at 3x on any screen, so the frost spreads as far in pt everywhere), bends it by a fitted bevel that folds content in from the middle at the rim, and tones it from tables over distance from the edge and normal angle that also carry the rim light, hairline and shadow. Those tables have a row per 3x device pixel and the rim light and hairline are about that thin, so below 3x each pixel near the edge averages finer samples (3 x 3 at 1x, 2 x 2 at 2x); one sample would bead the ring. It shares the Gallery's GPU device. A source whose photos move by the browser's own scrolling sets `scrolls` and wakes the glass only on scroll: that scrolling runs off the main thread, a frame ahead of the rects the glass reads, so while the photos keep moving the glass draws them a step ahead (without it, it trails a frame, 6.7 pt at 400 pt/s). Tinted live glass isn't modelled: a `tint-*` class on the Button keeps it static. Pressed, it pulls in 1px per side as static glass's surface does, at the same timing: a CSS `scale` on its canvas (`--live-glass-press`, set from the control's width), which the renderer reads off the canvas's box and draws at that size.
- `tools/glass-live/` is live glass's fixture (its `README.md` walks through the loop): `scenes.ts` writes `Scenes/scenes.json` (the overlay's masonry, a line grid, ramps, sawtooths, a step and flat tones), which the SwiftUI app and `/dev/live-glass` both lay out; `capture.sh` takes iOS 27 simulator captures; `fit.py` fits the material into `src/lib/live-glass-material.json` (generated and left unformatted; refit rather than edit it); `shoot.ts` captures `/dev/live-glass?scene=` at 3x in headless Chrome (playwright-core) and `diff.py` compares the two. Ramps measure where the bevel samples from, the step's line spread measures the frost, and the grid shows the fold. The `motion-*` scenes scroll three copies of the masonry under the glass at 400 pt/s: `record.sh` records the simulator (H.264, so compare against the floor `motion.py` reports), `motion.py offsets` places each frame on the strip, `motion.ts` renders the web at those offsets, and `motion.py diff`/`video` compare them. `capture.sh motion-light@<pt>` takes lossless stills along the strip, which `fit.py` fits with the rest. `lag.ts` screencasts the web while it really scrolls (`raf`, `wheel`, `touch`) and `motion.py lag` measures how far the glass trails the page. iOS glass has no temporal behaviour: a recorded frame matches a still at its offset. The bevel's pull runs from about 23 pt at the rim (so the rim shows content from near the middle, and a gap behind it sweeps out into a cap) to 0 by 14 pt in: iOS doesn't bend the middle at all, and any pull there magnifies and smears it. It is a monotone cubic (PCHIP) through its knots in `fit.py` and the shader alike, since a linear one creases the rim; `fit.py --bevel` refits the knots to the image error of both schemes. The frost works in a power space per scheme (`gamma`, about 1.56 light, 0.70 dark: the compose pass raises the backdrop, the glass pass undoes it after mixing), and its sharp share is the backdrop at half the 3x screen's resolution on even device pixels, read back bilinearly, as iOS's line spread shows; neither linear light nor a narrow Gaussian fits as well. `fit.py` holds the motion stills at 150, 450, 750, 1050 and 1350 pt out of its searches and reports them apart.
- `wrangler.jsonc` configures the Worker. Build output goes to `dist/`. Start prerenders `/` into a static asset; the Worker handles other URLs, including the 404. `public/_headers` sets asset caching. The Worker's entry is `src/server.ts`, Start's handler plus byte ranges for `/assets/*.webm` and `/assets/*.mp4`, which `run_worker_first` routes to it: static assets answer a `Range` with the whole file, and Safari won't play video served that way.
- Its `dev` environment is a second Worker, `imomadjid-com-dev`, on dev.imomadjid.com. `bun run build:dev` builds it (`CLOUDFLARE_ENV=dev`), with the dev tools on and the site kept out of search: every page has `<meta name="robots" content="noindex">`, and the `dev-tools` plugin appends `X-Robots-Tag: noindex` to the built `_headers` and drops the sitemap from `robots.txt`. Keep `robots.txt` allowing crawlers there, or they never see the noindex. The built `dist/server/wrangler.json` records the environment, so deploy it with `--config`, as `bun run deploy:dev` does.
- `tint-*` (`src/theme.css`) colors Buttons like SwiftUI's `.tint()`: `tint-red-500`, `tint-blue-100`, arbitrary values. No opacity modifier (a translucent tint reads as disabled); use a lighter palette step instead. It sets `--btn-tint*` variables, so it cascades to nested Buttons; primary fills with it, glass lays it between `--glass-fill` and a soft-light edge shine, and the label turns white below oklch L 0.75. Don't use `bg-*` for Button color: the fill is an inner span. `cn` doesn't merge two `tint-*` classes (registering a group needs `cn/config`, +45 KB JS), so pass one.
- `tools/glass-tints/` is a SwiftUI fixture (iOS and macOS 26+) rendering Liquid Glass tinted with Tailwind colors converted to Display P3. Generate with `xcodegen generate` there. `capture.sh` takes lossless 3x PNGs from an iOS 27 simulator named `GlassTints` (iPhone 16 Pro) into `<dir>/ref`; `shoot.sh` renders `/dev/glass` at 3x into `<dir>/web`; `tintdiff.py` diffs the tinted reference frames per region. Fit against simulator captures, not macOS: macOS glass can differ, and inactive macOS windows desaturate it. Simulator glass is close to, but not the same as, the iOS 26 device captures behind untinted glass, so tinted fits are relative to plain glass.
- Shaders are `.wgsl` modules loaded by vgpu's `wgslVitePlugin`; `bunfig.toml` preloads `tools/bun-wgsl-loader.js` so Bun tests can import them. vgpu render targets need whole-pixel sizes.
- iOS Safari 26+ clips `position: fixed` and `position: sticky` layers to the viewport between its status bar and toolbar (a sticky layer overscanned past each end is cut at the bars too; checked in the simulator with a marker at its top), and `viewport-fit=cover` doesn't change that: only the page's flow draws under the bars. It also collapses its toolbar only when the document scrolls, never a scrolling layer over it. The Sunlit layers stick on touch screens, overscanned 5rem past each end; `src/lib/light-frame.ts` maps the scene back onto the viewport-sized frame. Safari also fills the area under a bar with an opaque, unblurred band where the middle of that edge hits a fixed or sticky layer about the viewport's size or a dimming layer (a translucent background with no children); with a backdrop-filter the band takes the page's colour (WebKit's `fixedContainerEdges`). So on touch screens the See more overlay lies in the page's flow and the page scrolls it (`useOverlayScrollsPage`, from `useMediaQuery` in `src/lib/media-query.ts`; `holdPage` in `src/lib/dialog-layer.ts` pins `main` at its scroll until the overlay has gone), which lets the photos run under both bars and the toolbar collapse; it portals into a `contents` layer at the top of the body, and its dialog is `modal="trap-focus"` there, since a scroll lock would stop it. The backdrops (`dialogCoverClass`) are fixed and reach 5rem past each end of the viewport, too tall to count (a fixed layer that tall is clipped at the bars as a sticky one is, so sticking buys nothing). The backdrop's colour and blur sit in a child (`GalleryBackdropFill`), so it isn't a dimming layer. Safari bands the bars over a blurred backdrop in the page's colour, so on touch screens that child also lays a strip of the page's colour along each edge, fading into the blur, and the band joins it without a seam. The open photo's popup stays fixed and viewport-sized on purpose: its band covers the toolbar, where the clipped backdrop would leave the page showing unblurred. Keep the flight canvas `invisible` between flights: it covers the viewport, and Safari hit-tests through `pointer-events: none`. The iOS Simulator has no WebGPU adapter, so check layer extents there and the shader in the browser pane at a mobile size; Simulator Safari reaches the Mac's `localhost` directly (`xcrun simctl openurl <device> http://localhost:3000/`).

## Development and validation commands

Use Bun and update `bun.lock` with dependency changes. Node 26 is pinned in `.node-version` (fnm, CI) and `engines`; keep `@types/node` on the same major. See `README.md` and `package.json` for commands. Run `bun run deploy` only with deployment authorization.

## Coding style and naming

Let Oxfmt enforce formatting. Use PascalCase for React components and camelCase for functions and variables. Follow TanStack file-based route naming. Use type-only imports where appropriate.

Use Tailwind utilities for styling, and wrap a class string kept in a constant in `tw` (`src/lib/tw.ts`) so Oxfmt sorts it. Keep Oxfmt, Oxlint, and anti-slop settings in `vite.config.ts`, which `vp fmt`, `vp lint` and the Oxc editor extension read. Format with `bun run format` (`vp fmt`), never the bare `oxfmt` binary, which doesn't read `vite.config.ts` and falls back to its defaults (double quotes, semicolons). Do not add Biome. Treat `tools/oxlint/anti-slop/` as vendored code.

## Icons

- **Utility icons** (arrows, chevrons, close, external link, copy, menu): use Tabler via `@tabler/icons-react`. The Gallery overlay's close button is the first one.
- **Decorative or unconventional icons** (theme toggle, feature accents, anything the page features rather than just labels): draw Fill Duo icons with the `duotone-icons` skill in `.agents/skills/duotone-icons` (source: `imomadjid/duotone-icons`). Load the skill before drawing, and run its `lint.mjs` and `preview.mjs` scripts on the result. Put the icons next to their component, following `src/components/theme-icons.tsx`.
- Don't mix the two styles in one control. Size Tabler icons to match the Fill Duo 18px grid wherever they sit side by side.
- Restore or update local skills with `bunx skills experimental_install` and `bunx skills update`; `skills-lock.json` pins the source commit.

## Testing guidelines

Tests use `bun test` (`bun run test`). CI runs only `src/components` and `src/lib` tests and `tools/fluid-registry-files.test.ts` because the shader test needs a native WebGPU adapter. No coverage threshold is configured. For implementation changes, run `bun run check`, `bun run test`, and `bun run build` before review. Verify UI changes in a browser. For documentation-only changes, check formatting and verify affected instructions against the repository. A read-only audit does not require a build unless needed to investigate a finding. Use descriptive `*.test.ts` or `*.test.tsx` names for future tests.

Run `bun run doctor` when the task requests a full React audit or a React-related finding needs broader investigation. The full audit blocks errors; staged React Doctor warnings block commits. Review advisory findings before changing code. See `README.md` for hook and advisory tool details.

## Commits and pull requests

Use concise imperative messages with `feat:`, `fix:`, or `chore:` prefixes. Keep changes focused.

Commit on `master` in the main checkout, then push to `dev` first: `git push origin master:dev`. Pushing `dev` runs `.github/workflows/deploy.yml` and deploys dev.imomadjid.com for review. If `origin/dev` has commits `master` lacks, rebase `master` onto it before pushing. Pushing `master` itself runs the same workflow and deploys production, so push it only with deployment authorization, after the work has been checked on dev.

PRs should describe the change, link relevant issues, and report validation results. Include screenshots for visible UI changes. Never commit credentials, environment files, or generated build output.

## Fluid Functionalism surfaces

FF is a copy-in registry configured in `components.json`. Add components only when needed: `bunx shadcn@latest add @fluid/base/button --yes`. Prefer the Base UI variants (`@fluid/base/<name>`). Review source and dependencies before installation; do not overwrite local adaptations blindly.

- Keep the local `src/lib/utils.ts`, `surface-classes.ts`, and `surface-context.tsx`; restore them after `--overwrite`.
- The shadcn CLI mangles `src/styles.css` (self-referencing vars, keyframes inside `@theme`) and may rewrite `src/lib/utils.ts` or re-add `clsx`/`tailwind-merge`. Review the diff, merge tokens by hand, and keep `cn` re-exported from the `cn` package.
- FF's `src/lib/icon-context.tsx` and the `/dev` fixtures use `lucide-react`. Keep it to those files; production UI follows the icon rules above.
- `cn` resolves conflicts with tailwind-merge's default groups, so it reads the custom `text-display`/`text-title`/`text-body`/... sizes as text colors and drops one of them next to a color. Pass those through plain strings, or use the `text-[length:...]` forms in `src/lib/type-scale.ts`.
- FF components read neutral shadcn roles (`foreground`, `muted-foreground`, `border`, ...) defined in `src/styles.css`.
- The site uses FF's `pill` shape, set once by `<ShapeProvider defaultShape="pill">` in `__root.tsx`. FF components read it from context; no CSS reads the `--shape-input-radius` property the provider writes, and the base `:focus-visible` outline follows each element's own corners. The `/dev/components` shape switcher previews other shapes at runtime only.
- Add new FF registry files to `fluidRegistryFiles` in `tools/fluid-registry-files.ts` (`vite.config.ts` relaxes anti-slop rules there only), to `ignore.files` in `doctor.config.json`, to `ignoreFindings` in `.fallowrc.json`, and to the matching `@source` lists in `src/styles.css` (excluded) and `src/dev/dev.css` (scanned). `tools/fluid-registry-files.test.ts` fails if those lists drift. When a production page starts rendering an FF component, also move the runtime CSS it needs (spinner keyframes, `.scroll-fade`, `.scroll-divider`) from `src/dev/dev.css` into `src/styles.css`. `dev.css` links only under `/dev`, so site pages in dev show production CSS. Production CSS skips the playground and FF components; remove a file from the `@source not` list once a production page renders it.
- `src/theme.css` holds the shared dark variant and `@theme` mappings. `src/dev/dev.css` references it; it must not reference `src/styles.css`, or that sheet's `@source not` rules apply to the dev scan. `src/dev/dev.css` puts its utilities in the same `utilities` layer and scans every source, not only the playground, so it is a complete, ordered utility set that wins over `src/styles.css` on `/dev`; narrowing that scan lets its plain utilities override variants only `styles.css` emits.

The root provides level 1 and paints `bg-surface-1`. Surface colors and shadows live in `src/styles.css`; light mode uses shadows above white surfaces, while dark mode also increases background brightness. Activate dark tokens with `.dark` on `<html>`.

- Read the parent level with `useSurface()` from `#/lib/surface-context`. For custom overlays, use `normalizeSurfaceLevel(parent + offset)` from `#/lib/surface-classes`: menus/popovers use `+2`, dialogs use `+4`, capped at 8.
- Paint the container with `surfaceClasses(level)` and wrap its children in `<SurfaceProvider value={level}>`. Context alone does not paint a background. Preserve this context through portals.
- Keep FF components' existing elevation logic. Do not add a second offset around them.
- Use `surfaceClasses(level, shadowLevel)` when a component deliberately keeps its shadow depth separate. Avoid arbitrary background colors or shadows for elevated panels.
- Never interpolate `bg-surface-${level}` or `shadow-surface-${level}`. Use the literal lookup helpers so Tailwind emits the classes. Use `bg-hover` and `bg-active` for interaction overlays.
- Check nested surfaces in light and dark modes, including focus and clipping. See [upstream surface rules](https://www.fluidfunctionalism.com/docs/surfaces).
